## 3. Blocking structural defect

The manifest declared 48 parent clusters, each containing six scenarios (three per role). The cluster registry used IDs of the form:

`family_id|difficulty_stratum`

However, each scenario row used:

`family_id|difficulty_stratum|evaluation_role`

Consequently, the scenario rows contained 96 distinct role-fragmented `cluster_id` values, while the registry contained 48 IDs. The declared cluster IDs could not be joined to the scenario rows, and the intended task-family × fault-stratum statistical unit was not represented consistently.

This is a manifest-integrity defect, not evidence of an algorithmic result. The v1 manifest hash is therefore **not frozen** and must not be used for an optimizer run.

## 4. Correction

The candidate generator is versioned to `d079-train-only-difficulty-strata-v2`:

- Scenario `cluster_id` is now `family_id|difficulty_stratum`.
- `evaluation_role` remains a separate field.
- The validator now checks the 48-cluster registry against scenario rows, six rows per cluster, three rows per role, label/family/stratum consistency, role and label counts, scenario-ID structure, evidence hashes, and canonical manifest SHA-256.
- Regression tests explicitly reject role-fragmented cluster IDs.

The v2 candidate must be regenerated by CI and independently audited before a new `d079_manifest_lock.json` is created. The old v1 hash must never be silently reused.
